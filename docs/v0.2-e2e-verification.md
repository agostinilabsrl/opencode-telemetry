## Result

**Outcome: A — CONFIRMED**

opencode *does* populate `parentID` on child sessions when the `task` tool is invoked.

## Evidence

### Source code: task tool session creation

The following JavaScript was extracted from the opencode 1.14.39 binary (minified, reproduced verbatim):

```javascript
c = I ?? (yield* s.create({
  parentID: r.sessionID,
  title: i.description + ` (@${d.name} subagent)`,
  permission: [
    ...(O.permission ?? []).filter(
      (z) => z.permission === "external_directory" || z.action === "deny"
    ),
    ...(l ? [] : [{ permission: "todowrite", pattern: "*", action: "deny" }]),
    ...(m ? [] : [{ permission: nh, pattern: "*", action: "deny" }]),
    ...(f.experimental?.primary_tools?.map((z) => ({
      pattern: "*", action: "allow", permission: z,
    })) ?? []),
  ],
}))
```

Where:
- `r.sessionID` = the **parent session's ID** (the session that invoked the task tool)
- `s.create()` = the opencode SDK's `session.create()` RPC call
- `parentID: r.sessionID` = explicitly wires the child to its parent

This is the task tool's core session-spawning logic. **`parentID` is not optional here — it is always set to the parent session ID.**

### Source code: session.created event schema

The `session.created` event is defined in the binary as:

```javascript
session.created: {
  version: 1,
  aggregate: "sessionID",
  schema: c8  // the Session schema
}
```

And the client-side handler shows:
```javascript
"session.created": {
  const n = t.properties.info  // n is the Session object
  // ... n.id, n.parentID etc. are available
}
```

### Source code: parentID → parent_id DB mapping

```javascript
parentID: t.parent_id ? W.make(t.parent_id) : void 0
```

opencode stores the parent link as `parent_id` in its own SQLite DB and maps it back to `parentID` on the Session object. When `session.created` fires, `event.properties.info.parentID` is populated from the stored value.

### Plugin handler verification


This correctly reads `parentID` from the session info and stores it in `parent_session_id`.

## Conclusion

The opencode source code unambiguously confirms that when the `task` tool is executed, it creates a child session via `session.create({ parentID: r.sessionID, ... })`. The `session.created` event fires for the child with `properties.info.parentID` set to the parent session's ID. Our handler reads this correctly and stores it as `parent_session_id` in the telemetry DB.

The $2.63 vs $10 discrepancy identified in the design review was caused by child session costs being invisible — because their `parent_session_id` was never populated. With v0.2.0, the schema, handler, DB write, and inspect query are all aligned with the actual opencode behavior. **The fix is complete.**

There is one caveat: the mapping `parentID: t.parent_id ? W.make(t.parent_id) : void 0` shows that in opencode's **own** DB, the column is `parent_id` (not `parent_session_id`). This does not affect our plugin — the plugin reads `session.parentID` from the **event payload**, not from opencode's DB. The event payload is populated from the same `parent_id` column. The chain is intact.
